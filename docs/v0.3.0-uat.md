# cogo v0.3.0 — user acceptance tests

Real-codebase UATs for the v0.3.0 release. The point of v0.3.0 was
behavioral (the `-customtools` model, structured tools, parallelism
mandate); the probe in `dev/parallel-probe/` measured *"is the model
batching tool calls?"* These UATs answer the bigger question:
**does this actually produce good code work on real codebases?**

Cogo's own tree is the primary subject. The UATs are ordered by what
they exercise and by risk to the working tree.

## Setup, common to all

```sh
git clone https://github.com/go-steer/cogo /tmp/uat-cogo
cd /tmp/uat-cogo
# Use a throwaway clone so failed edits / accidental commits can be
# discarded without consequence.

# Source Vertex creds
source ~/scripts/gemini.sh && unset GEMINI_API_KEY

# Confirm v0.3.0 binary
cogo --version    # should be v0.3.0
```

For each UAT, **run with `--debug 2> trace.log`** so the tool-call
trace is captured. Reading the trace tells you *what* the agent did,
not just what it said. Specifically grep for:

- `→ grep` — confirms item 2 (grep available, model picked it)
- `→ read_many_files` — confirms item 3 (batch tool preferred)
- `→ bash` — note when bash was chosen and whether a structured
  alternative would have been better

## Tier 1 — Analysis only (low risk, builds confidence)

These don't touch the codebase. If cogo can't answer these well, the
harder tiers won't fly.

### UAT-1.1 — "Explain this module to me"

```text
cogo -p "Explain what internal/permissions/ does and how the pieces
fit together. Cover the Gate, Policy, PathScope, the bash denylist,
and the recently-added /allow + /deny slash commands. Be specific
about which file does what."
```

**Pass criteria:**

- Identifies all five concepts and the file each lives in.
- Mentions the gate-pattern relationship (Gate consults Policy;
  Policy is mutated by `/allow`).
- Doesn't hallucinate functions or files that don't exist.
- Used `grep` and `read_many_files` (not 10 sequential `read_file`
  calls). Check `trace.log` for `→ grep` and `→ read_many_files`.

**Why it matters:** Validates item 2 (grep/glob available) and item 3
(read_many_files preference). The model has to *choose* the right
tool for a "tell me about this module" task.

### UAT-1.2 — "Find the bug pattern across files"

```text
cogo -p "Find every place in this codebase where we use sync.Mutex
without a defer Unlock() in the same function. List file + line +
function name."
```

**Pass criteria:**

- Uses `grep` for `sync.Mutex`, then `read_file` or `read_many_files`
  to inspect candidates.
- Either finds the matches accurately OR honestly says "0 found" if
  there aren't any (don't tolerate fabricated hits).
- Reports line numbers that actually point at `sync.Mutex`
  declarations.

**Why it matters:** Tests grep + structured reading + the model's
discipline about hallucinations. AST-level reasoning would be more
accurate but cogo doesn't ship `view_file_outline` yet (that's
v0.4.0); this is the test that says "with grep + reads, can the model
still get static-analysis questions right?"

### UAT-1.3 — "Architecture summary"

```text
cogo -p "Generate an architecture overview of this codebase. List the
top-level packages under internal/, what each owns, and the main
dependency relationships between them (e.g., 'tui depends on agent
depends on tools'). Cite specific imports as evidence."
```

**Pass criteria:**

- Names at least 10 packages correctly.
- Dependency claims cite actual `import` statements (use `trace.log`
  to confirm the agent read the relevant `.go` files).
- Doesn't invent packages (e.g., "internal/runtime" doesn't exist).

**Why it matters:** Exercises broad codebase navigation. Without
`read_many_files`, this is N×read_file. With it, the agent should
batch.

## Tier 2 — Targeted edits (real changes, easily reverted)

These produce a diff. Run `git diff` after each to inspect;
`git checkout .` to revert.

### UAT-2.1 — "Add a small feature"

```text
cogo -p "Add a new slash command /version to the TUI that prints the
cogo version and build info. Wire it up the same way /quit is wired
(commands.go, palette.go, update.go). The version string lives in
cmd/cogo/version.go — use versionString()."
```

**Pass criteria:**

- Touches all three files (commands.go, palette.go, update.go).
- Doesn't break the build (`go build ./...`).
- Doesn't break tests (`go test ./internal/tui/...`).
- Follows the existing slash-command pattern correctly —
  `SlashVersion` constant, alias map entry, palette entry, switch
  case.
- If `versionString()` is in `package main` (cmd/cogo) and TUI can't
  import it cleanly, the agent either (a) refactors cleanly or (b)
  honestly reports the import-path problem and suggests an
  alternative — does NOT silently introduce a circular import.

**Why it matters:** Canonical "add a feature with N coordinated
edits" task. v0.3.0's `read_many_files` should let the agent see all
three files in one batch, and the parallelism mandate should
encourage parallel reads/edits.

### UAT-2.2 — "Fix a tiny bug I'll plant"

Pre-step: introduce a deliberate bug:

```sh
sed -i 's/if cfg == nil/if cfg != nil/' internal/tools/register.go
# inverted check
```

Then:

```text
cogo -p "tools.Build is returning nil-pointer panics on every call.
Find and fix the bug. Don't change anything beyond what's necessary."
```

**Pass criteria:**

- Locates the bug.
- Fix is exactly the inversion (or a semantically equivalent
  rewrite); not a sprawling refactor.
- `go test ./internal/tools/...` passes after the fix.

**Why it matters:** Bug-hunting from a symptom — exercises grep,
targeted reading, and edit-discipline. Scope-creep is a common
failure mode (the agent adds defensive nil checks all over the
place); this UAT catches that.

### UAT-2.3 — "Refactor without changing behavior"

```text
cogo -p "Extract the per-tool truncation cap lookup from
internal/tools/file.go (currently inline in capsFor) into a new
exported function internal/tools/caps.go::Caps(cfg, name,
defaultBytes, defaultLines) that returns a struct. Update all call
sites. All existing tests must still pass."
```

**Pass criteria:**

- New file at the expected path.
- All call sites updated (grep for `capsFor` to verify zero remaining
  references).
- Tests still pass (`go test ./internal/tools/...`).
- No behavioral change — the diff should be moves and renames, not
  logic.

**Why it matters:** Multi-file mechanical refactor. Without good
batched reads, the agent does this one file at a time and often loses
track. With `read_many_files` + grep, it should be quick and
accurate.

## Tier 3 — "Where it embarrasses itself" — break things on purpose

These are the tests that surface where v0.3.0 falls short. Expect
some failures; the goal is to characterize them so v0.4.0's
quality-floor work targets the real pain.

### UAT-3.1 — "Edit something that should fail compilation"

```text
cogo -p "In internal/agent/agent.go, rename the WithTools function to
WithToolList everywhere it's used across the codebase."
```

**Pass criteria (pre-v0.4.0):**

- Agent finds all call sites via grep (8+ across cogo).
- Updates them all.
- **The interesting question:** does it run `go build` after to
  confirm? Today (v0.3.0, no post-edit verification gate) it probably
  does NOT. The compile failure surfaces later when *you* try to
  build.
- Document what happens. This is exactly the failure mode that
  v0.4.0's post-edit verification gate fixes.

**Why it matters:** Headline argument for v0.4.0 item 1. If the agent
here ships broken code and doesn't notice, you have a
screen-recordable "look at this thing v0.3.0 misses, v0.4.0 fixes"
demo.

### UAT-3.2 — "Multi-turn task — does context carry?"

In TUI mode (`cogo`):

1. `Show me how the permission gate decides whether to prompt the
   user. What method is it and what's the decision tree?`
2. (after the answer:) `Now add a third decision branch: if the
   request is a tool with a verb starting with "git", auto-approve
   even in ask mode.`
3. `Wait — that's a security regression. Revert it and instead make
   it require an extra prompt with a stronger warning.`

**Pass criteria:**

- Step 2's edit lands.
- Step 3 correctly reverts step 2's specific change (not the whole
  file) and adds the stronger-warning prompt path.
- Agent doesn't re-read `gate.go` from scratch each turn — should
  keep state from earlier reads. (Pre-v0.4.0 cache, this is partly
  luck — the agent re-reads but might be smart about it.)

**Why it matters:** Multi-turn refactor with course-correction. Tests
the model's working memory + ability to surgically revert. v0.4.0's
workspace shadow makes the re-reads cheap.

### UAT-3.3 — "Cross-package consequences"

```text
cogo -p "Add a new field 'Description string' to the
permissions.PromptRequest struct. Surface it in the TUI's permission
modal (renderConfirmModal in internal/tui/view.go) as a second line
below the existing detail line. Update all PromptRequest constructors
I can find to populate Description with something reasonable."
```

**Pass criteria:**

- Struct field added.
- Modal renders the new line.
- ALL constructors updated (grep for `PromptRequest{` — there are
  several, including in tests).
- Tests still pass.
- Watch for: does the agent miss test-only constructors? That's a
  common cogo-specific gotcha.

**Why it matters:** Wide-blast-radius edit. The agent needs to find
every constructor (parallel grep helps) and update each. Test
fixtures using `PromptRequest{}` (no explicit fields) are easy to
miss because they don't show up in a naive `Description:` grep.

### UAT-3.4 — "Question with a wrong premise"

```text
cogo -p "Why does cogo use Redis to cache file reads?"
```

**Pass criteria:**

- Agent says "cogo doesn't use Redis" (and ideally cites what cogo
  *actually* does for caching — nothing today; that's v0.4.0's
  workspace shadow).
- Does NOT fabricate Redis usage or invent a `redis.go`.

**Why it matters:** Hallucination check. Easy to write, brutal to
fail.

## Tier 4 — "Production-shaped" longer-running tasks

These take 5-15 minutes per run; do one when you want a deeper
signal.

### UAT-4.1 — "Implement a small feature from a real plan"

Pick something well-scoped from `docs/v0.4.1-plan.md` — item 3
(model pinning) is small:

```text
cogo -p "Read docs/v0.4.1-plan.md item 3 ('Model pinning on resume')
and implement it. Modify the relevant files. Include a unit test.
Don't worry about wiring it into the resume flow — just the
standalone behavior: when an Agent is constructed with a Model field
overriding cfg.Model.Name, that override pins."
```

**Pass criteria:**

- Reads the plan doc.
- Identifies the right files to edit (probably
  `internal/agent/agent.go` + a new test).
- Implementation matches the plan's described behavior.
- Test asserts the pinning logic.
- `go test ./internal/agent/...` passes.

**Why it matters:** End-to-end. Plan-doc reading + targeted
implementation + test authorship. The closest to "real cogo
development workflow." If this works, v0.3.0 has crossed a real bar.

### UAT-4.2 — "Run the parallel-probe and write up the result"

```text
cogo -p "Run go run ./dev/parallel-probe --task=multiread
--model=gemini-3.1-pro-preview-customtools, then
./dev/parallel-probe --task=multiread
--model=gemini-3.1-pro-preview, and write a short markdown summary of
the difference in tool-call behavior between the two models. Save it
to /tmp/probe-result.md."
```

**Pass criteria:**

- Runs both commands (bash, with permission prompts handled).
- Captures the histograms.
- Summary is accurate: mean batch, wall time, tool choice
  differences.

**Why it matters:** Exercises bash + read + write all in one. Also
surfaces whether the agent handles permission prompts gracefully in
long sessions.

## What to grade on, holistically

Independent of pass/fail per UAT, these are the signals worth
tracking across the run:

1. **Tool choice quality** — does the agent reach for
   `grep`/`glob`/`read_many_files` first, or does it default to
   `bash grep`? (Trace check.)
2. **Batch behavior** — how many tool calls per turn on multi-file
   tasks? Should average > 1 with v0.3.0 levers.
3. **Edit discipline** — does it scope its edits to what was asked,
   or does it sprawl?
4. **Build/test self-awareness** — does it check `go build ./...`
   after edits unprompted? (Today: probably no. v0.4.0 fixes this.)
5. **Honesty under wrong premises** — UAT-3.4 and similar; does it
   push back when the question is malformed?
6. **Permission UX** — how does it feel? Are you constantly approving
   stuff that should be in the bundles? Does the new built-in
   allowlist actually cover the common cases?

## Suggested order

| Order | Tier | Time | Why |
| --- | --- | --- | --- |
| 1 | Tier 1 (1.1, 1.2, 1.3) | ~30 min | Validates the basics; if these fail, harder tiers won't fly |
| 2 | Tier 2 (2.1, 2.2, 2.3) | ~1 hour | Targeted edits exercise the v0.3.0 wins under real-edit pressure |
| 3 | Tier 3 (3.1-3.4) | ~1 hour | Surfaces what v0.4.0 needs to fix; write down failure modes — they become v0.4.0's acceptance criteria |
| 4 | Tier 4 (one of 4.1 or 4.2) | ~15 min | Production-shaped depth check |

## What to do with the results

- Each Tier 3 failure mode is a candidate v0.4.0 acceptance criterion.
  Capture concrete observations: "agent renamed `WithTools` →
  `WithToolList` and didn't notice the build broke in 4 packages."
  That sentence is the test for v0.4.0's post-edit verification gate.
- Each "tool choice quality" miss (agent used bash when grep would
  have worked) is a candidate prompt or tool-description tweak.
  Collect verbatim trace excerpts.
- Each hallucination (Tier 3.4 or surprises in Tier 1) is a candidate
  prompt-tightening or test fixture.

If a UAT yields a clear, repeatable failure, file it as a GitHub
issue with the trace.log attached. v0.4.0's branch can close them as
the relevant work lands.
